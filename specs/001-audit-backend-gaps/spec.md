## User Scenarios & Testing *(mandatory)*

### User Story 1 - 以 PRD 为依据看清当前能力 (Priority: P1)

作为 PathMate 产品负责人，我希望得到覆盖全部 PRD 需求的实现对照表，知道哪些用户流程已经具备基础、哪些只有展示或模拟，以及哪些没有对应实现，以便确定后续开发范围。

**Why this priority**: 没有需求到实现的证据对照，团队会重复建设已有能力，或把演示效果误认为可交付的功能。

**Independent Test**: 选取求助、位置安全和健康打卡三个需求领域，核对原文、现有行为与结论是否逐项对应；这份局部对照表本身即可帮助团队判断开发方向。

**Acceptance Scenarios**:

1. **Given** PRD 和已有前后端材料，**When** 负责人查看对照表，**Then** 每条独立需求都有编号、PRD 页码或章节、预期用户结果、实现证据、实现状态和后端处置建议。
2. **Given** 页面有按钮或数据展示但没有完整处理链路，**When** 评估该需求，**Then** 结果明确标注展示、模拟或局部实现，指出缺失环节，不按完整能力判为可保留。
3. **Given** PRD 同时描述手机原型、明确模拟功能和后续扩展，**When** 汇总覆盖情况，**Then** 分开注明范围，后续手表或机构能力的缺失不会混入手机原型完成率。
4. **Given** PRD 内同一功能描述互相冲突，**When** 建立评估基线，**Then** 记录双方出处及影响，采用章程已批准的基线，不把已确认事项重新标为假设；未解决的冲突单列待决策。

---

### User Story 2 - 判断已有后端的保留与修复边界 (Priority: P1)

作为接手后端的开发者，我希望了解每项现有能力能否复用、存在什么缺陷，以及缺陷对长者安全、隐私和家属照护的影响，以便修复现有成果并避免无依据重写。

**Why this priority**: 数据保存或查询的基础可能值得保留，但权限、隐私和告警链路的缺陷会影响整个照护流程。

**Independent Test**: 单独评估账号与长者资料管理，复核正常操作、两账号隔离及数据归属的证据，确认报告能给出有条件的复用建议和可验收的修复结果。

**Acceptance Scenarios**:

1. **Given** 后端已有某项处理能力，**When** 评估正常和失败场景，**Then** 建议说明保留的具体部分、前提和验证程度；需要修复的部分单列，不因局部问题否定全部已有成果。
2. **Given** 两个不同家庭账号或不同照护角色，**When** 检查资料访问与操作范围，**Then** 报告明确记录是否隔离、证据、未验证条件及风险，不把联系人列表当作多人协同授权已完成。
3. **Given** 长者关闭位置或健康共享，**When** 检查相关流程，**Then** 报告分别说明上报、家属展示和后续事件是否遵守关闭状态；未找到控制能力时记录相应缺口。
4. **Given** 服务依赖尚不可用的运行条件，**When** 验证无法完成，**Then** 标记为未验证或验证阻塞，列出缺少条件和复核步骤，不直接判为未实现或验证通过。

### User Story 3 - 主动发现代码问题与章程差异 (Priority: P1)

作为接手项目的开发者，我希望检查现有前后端中的实际缺陷、章程差异及可改进之处，
即使 PRD 没有列出相关功能，也能了解影响和证据，避免把功能对照完成误认为代码没有问题。

**Why this priority**: 已存在的支撑流程、异常处理和数据操作同样会影响可靠性与维护，必须主动检查。

**Independent Test**: 选取一项 PRD 未直接规定的现有支撑行为，核对检查记录是否包含适用的正常与异常情形、判断依据及验证限制；即使未发现问题，覆盖记录也能说明检查了什么。

**Acceptance Scenarios**:

1. **Given** 代码存在 PRD 未明确描述的支撑行为，**When** 检查其输入、状态变化、失败处理和数据一致性，**Then** 发现被记录为代码缺陷、章程违反或可选改进，不伪造产品需求；未发现问题也记录覆盖及验证限制。
2. **Given** 一项问题同时导致需求未满足并违反章程，**When** 登记发现，**Then** 使用一个发现编号、一个主分类及交叉标签，分别关联需求和章程条款，注明证据、影响、优先级和验证程度，不重复统计。
3. **Given** 建议仅出于个人偏好，或只因缺少环境而无法复现，**When** 形成结论，**Then** 前者不能列为必要修复，后者标为未确认或验证阻塞；两者都不得声称为已证实缺陷。

---

### User Story 4 - 形成可交接的缺口与优先顺序 (Priority: P2)

作为项目协调者，我希望拿到一份有证据、可排序的修复与新增工作清单，清楚知道依赖关系、完成条件和待确认决策，以便进入后续规划。

**Why this priority**: 评估必须落到下一步可安排的工作，而不是只列功能名称或笼统说需要完善。

**Independent Test**: 选取一个修复项和一个未实现项，让接手者仅凭交付资料找到需求来源、理解影响并说明如何验收。

**Acceptance Scenarios**:

1. **Given** 一项能力需修复或未实现，**When** 查看缺口条目，**Then** 能找到关联需求、现有与目标行为差异、影响、优先级理由、依赖、预期完成结果及验证方式。
2. **Given** 核心安全或隐私问题与生活辅助扩展同时存在，**When** 排序工作，**Then** 前者优先，并区分业务紧急程度和证据确定程度。
3. **Given** 评估已完成，**When** 团队审阅交付资料，**Then** 保留清单、修复清单、未实现清单与需求对照表可相互追溯，且待验证事项不会被包装成已确认结论。
4. **Given** 多项后端工作有前置依赖或涉及公共契约、服务职责和数据变更，**When** 查看后续建议，**Then** 能区分可复用基础、必要修复和缺失能力，找到依赖顺序、兼容性影响、迁移回滚要求及需要用户确认的决策；本阶段不执行开发。
5. **Given** 某条建议只是可选改进，**When** 查看开发交接资料，**Then** 该建议独立列出且标为待采纳，不被自动纳入必要修复、必做新增范围或完成率分母。

### Edge Cases

- 输入路径与实际文件名不同：确认实际对应关系，记录来源，不创建空材料代替。
- 仅有展示、固定数据、演示数据初始化或状态更新：分别说明能力边界，不能认定真实事件产生和通知已完成。
- 需求由长者端本地完成：标注端侧职责及后端是否需要参与，避免制造并不存在的后端缺口。
- 只有客观体征记录，没有主观身体状态打卡：两者分别评估，不能相互替代。
- 数据为空、记录过期、定位权限关闭或设备离线：区分正常空态、授权关闭、旧数据和处理故障。
- 同一事件重复提交、多人响应或主照护者未响应：检查重复处理、协同结果与转交能力，注明不存在或未验证的环节。
- 多个长者切换、未授权长者标识或删除长者：检查归属、误选、关联资料处理与访问边界。
- 香港日期跨日导致行程或统计范围变化：记录本地时间语义与当前行为差异。
- PRD 没有确定通知时限、默认阈值或存在号码冲突：记录待定条件，不把自行猜测的数值当成原文要求。
- 一个发现同时属于需求缺口、代码缺陷和章程违反：指定主分类并关联其他标签，按唯一编号去重；发现分类与保留/修复/新增处置分别表达。
- 现有代码行为偏离章程，但只是历史实现：依旧记录适用条款的差异，不因其已有而认定合规，也不自动授权重写。
- 没有发现某类问题：给出检查范围、检查方式和限制，不能由“零发现”推断不存在未检查的缺陷。
- 某项优化可能破坏公共契约、改变服务职责或需迁移数据：记录影响、依赖、回滚要求和待确认决策，不因标为改进就绕过章程。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 评估 MUST 以实际 PRD 文件、已批准章程和现有前后端材料为输入，记录材料路径、评估日期、章程版本、代码版本标识或可复核快照依据及材料缺失；最终报告能明确其结论适用于哪一份材料。
- **FR-002**: 评估 MUST 将 PRD 中每条可独立验收的功能、权限、隐私、可靠性和无障碍要求编号并注明出处；背景、竞品与举例不得自动视作交付要求。所有排除项 MUST 说明理由。
- **FR-003**: 对照表 MUST 区分手机原型核心、PRD 明确要求的模拟能力、后续扩展和范围待定项。扩展包括手表、机构以及便民/医疗预约等内容，仍须记录现状，但独立汇总。
- **FR-004**: 每条需求 MUST 记录预期行为、现有行为、证据位置、实现状态、验证程度、后端相关性及处置建议。实现状态为完整实现、部分实现、仅展示/模拟、未发现实现或待确认；验证程度为已运行验证、仅静态证据或验证阻塞，不能相互替代。
- **FR-005**: 评估 MUST 给出可保留、需修复、尚未实现三类后端处置清单；端侧独立能力或无法判定项单列说明。同一用户能力可拆成多个环节，保留其已有部分并分别列出修复或新增工作。
- **FR-006**: 可保留项 MUST 有满足对应需求的行为证据、复用边界和依赖条件；仅静态审查的建议必须标为候选保留。未发现实现项 MUST 记录检查范围和缺失环节；不能仅凭页面名称或缺少运行环境判定。
- **FR-007**: 评估 MUST 覆盖账号与角色、长者与照护者关联、联系人、资料和配置管理，以及注册、登录、退出、身份验证、跨账号隔离和未授权操作。PRD 未规定而现有实现引入的支撑能力应标为支撑项，不伪造 PRD 出处。
- **FR-008**: 评估 MUST 覆盖主安全圈、多个安全点位、熟悉/陌生站点管理和模拟进入、提醒开关、越界、滞留及提前提醒、近七天行踪和事件关联；分别检查配置、事件产生、长者提醒、家属接收和记录链路。
- **FR-009**: 评估 MUST 覆盖 SOS 防误触及确认、不舒服求助、时间与位置附带、分级提醒、主照护者响应、备用照护者转交和受限可见性。演示求助不得视为真实接警；验证不得拨打真实急救电话或发送真实求助。
- **FR-010**: 评估 MUST 覆盖八种主观健康状态、固定生活提示、七天/三十天汇总、家属确认跟进、即时文字叮嘱与长者接收；区分生活参考、客观体征展示和手表扩展，不将它们视作同一需求。
- **FR-011**: 评估 MUST 覆盖五种模拟天气场景及双端提示、语言同步、两种提醒播报模式、布局锁定、首次隐私说明、长者位置/健康共享开关和关闭后的家属空态。真实天气接入应与原型模拟分开判定。
- **FR-012**: 评估 MUST 追溯相关前端操作到后端行为、保存/读取结果与接收方结果，标注端侧功能、断开的交互、未被使用的后端能力及默认数据来源；地图或语音能力存在不等于后端事件流完成。
- **FR-013**: 每个必要修复或缺失能力条目 MUST 给出现状与目标差异、用户影响、关联需求或章程条款或现有行为依据、优先级及理由、依赖、完成条件和验证场景。优先级分为 P1 核心安全/隐私、严重数据问题或阻断流程，P2 核心流程完整性或影响可靠性/维护的必要修复，P3 非阻断的辅助及扩展；按实际影响判定，不由分类直接决定。可选改进也须标注优先级，但其优先级不等于开发承诺；不要求本阶段估算工期。
- **FR-014**: 验证 MUST 包含主要成功路径、输入异常、无数据、授权关闭、跨账号/角色访问、离线或依赖不可用、重复事件等适用情形。报告记录验证方式、结果与限制，静态判断不能表述为运行成功。
- **FR-015**: 需求冲突 MUST 并列记录出处、影响、已批准决策或未解决问题。评估 MUST 遵循章程 v1.0.1 的基线：默认只在围栏进出时上传位置；提醒模式不持续监听麦克风，主动语音操作须另行授权；手机原型不依赖手表，手表单列扩展。未解决的规则或新发现的冲突单列交由用户确认，不擅自变更基线。
- **FR-016**: 最终交付 MUST 包含评估摘要、完整需求对照表、三类后端清单、主动检查覆盖记录、四类发现登记、章程逐条核对结果、验证证据与阻塞、需求冲突与待决策事项、按优先级及依赖排序的后续建议，并记录各类数量及统计分母；一条需求有多种环节时不得重复算作多条完整完成需求。PRD 覆盖率、发现数量与可选建议数量分别统计。
- **FR-017**: 本任务 MUST 只交付评估资料和后续工作建议；不修改已有业务实现、不重写后端、不新增产品功能、不部署、不接入真实硬件，不修改真实用户数据。后续修复和开发应另行规划。
- **FR-018**: 评估 MUST 主动检查现有前后端代码及支撑材料，不限于 PRD 功能。检查范围至少包括全部用户输入入口及适用验证、访问控制与数据归属、业务状态及重复/并发操作、错误与异常路径、数据一致性及关联删除、敏感数据使用、配置与资源生命周期、公共契约与调用方一致性、服务职责、代码文档和运行/验证/迁移材料。每类 MUST 记录检查对象、方法、结果、未覆盖范围及原因；采用与影响相称的验证，不要求保证发现所有潜在问题。
- **FR-019**: 每项发现 MUST 有唯一编号和一个主分类，并可使用交叉标签。需求缺口指有效需求缺失、部分满足或与已确认需求有偏差；代码缺陷指现有行为存在可举证的错误或可靠性问题，即使 PRD 未描述也可成立；章程违反指与已批准条款或基线不符；可选改进指没有证明违反有效需求、章程或存在实际缺陷，但有可说明的收益的建议。待验证疑点 MUST 明示为未确认，不得伪装成已证实发现。
- **FR-020**: 四类发现的每项记录 MUST 包含主分类及交叉标签、前端/后端/跨端归属、问题或建议、预期与现状、可复核证据及位置、影响、优先级理由、验证程度、关联需求/章程条款或独立行为依据，以及复现或复核条件。可选改进须给出收益依据和代价/风险；静态证据支持什么、尚未证明什么必须明确。
- **FR-021**: 评估 MUST 按章程七项原则和三项基线逐条记录符合、有差异、明确批准的例外或尚未验证，并给出证据和限制。检查包括模拟标识、风险相称验证、全部输入验证、完整代码文档、公共契约兼容、现有服务边界、数据库迁移回滚计划；没有相关迁移时可标为本次不适用并说明检查范围，不得假造违规。模板示例、未采纳候选原则及个人技术偏好不得作为章程违反的依据。
- **FR-022**: 后端开发交接 MUST 将可复用基础、必要修复、缺失能力、可选改进和待确认决策分别列出；必要修复包括有依据的代码缺陷或章程差异，不限于 PRD 缺口。每项拟开发工作 MUST 关联发现或需求、服务职责、前置依赖、建议顺序、验收结果及兼容性影响；涉及未来数据迁移时说明所需回滚计划，涉及职责变更或不兼容能力时列为用户待确认事项。纯前端问题单列，跨端问题说明后端依赖，不自动变成后端工作。
- **FR-023**: 可选改进 MUST 保持独立的待采纳状态；只有用户明确确认后才能进入后续必做范围，不得计入必要修复、缺失能力或必做完成率。评估建议和依赖顺序仅供后续规划，不授权在本任务内执行修复、重构、迁移或部署。

### Key Entities *(include if feature involves data)*

- **需求条目**：独立用户结果及其编号、原文出处、所属范围、角色、验收条件和冲突关系。
- **能力评估项**：需求对应的现有行为、前后端职责、实现状态、验证程度、证据及处置建议；一个需求可对应多个环节。
- **证据记录**：材料版本、文件位置或观察记录、验证情形、实际结果、限制与复核条件，不包含真实个人敏感资料。
- **缺口条目**：修复或新增工作的差异、影响、优先级、依赖、预期结果及验收方式。
- **发现记录**：唯一编号、主分类、交叉标签、前后端归属、证据、影响、优先级、验证程度和复核条件；与需求及章程条款关联，允许无 PRD 对应项。
- **检查覆盖记录**：主动检查领域、对象和材料、方法、发现或未发现问题、未覆盖范围与限制。
- **章程核对项**：适用原则或基线、符合/差异/例外/未验证结论、证据及适用性说明。
- **开发交接项**：可复用基础或拟开发工作、关联发现、服务职责、依赖顺序、验收结果、兼容性与迁移风险、待确认决策及是否已采纳。
- **待决定事项**：原文矛盾或缺少规则、可能影响、暂用假设、需要团队决定的具体问题。
